# Release-readiness audit — 2026-08-21

## Decision

**Approve `v0.1.0` only as a prototype/research package release. Do not approve a vehicle-facing, safety-critical, or production deployment.**

This assessment examined the repository source, test suite, packaging path, CI/release workflows, container publishing configuration, and deployment manifests. It is an engineering readiness assessment, not a safety assessment or certification.

## Evidence collected

| Control | Result | Evidence |
|---|---|---|
| Source tests | Pass | 60 passed; 97.70% coverage using Python 3.12.13; benchmark tests intentionally excluded from the release gate |
| Package build | Pass | `python -m build` produced `autoguard_ai-0.1.0.tar.gz` and `autoguard_ai-0.1.0-py3-none-any.whl` |
| Package metadata | Pass | `python -m twine check dist/*` passed for both artifacts |
| CI dependency audit | Pass | `python -m pip_audit -r requirements-ci.txt` reported no known vulnerabilities at audit time |
| Static analysis | Pass with scope caveat | Bandit medium/high gate reported no issues; mypy completed with `--ignore-missing-imports` |
| CI/release reproducibility | Implemented | Release workflow tests, builds, checks metadata, creates checksums, uploads artifacts, and creates a GitHub build attestation |

Local validation used `--basetemp .pytest-tmp` because the host sandbox denied its user-level temporary directory. The command, test count, coverage, and package checks are reproducible through [REPRODUCIBILITY.md](REPRODUCIBILITY.md).

## Remediated in this release hardening change

| Priority | Finding | Remediation |
|---|---|---|
| P0 | `setup.py` built only a CUDA extension, forcing Torch/CUDA for the core install and shipping no normal Python package | Added PEP 517/621 package metadata, CPU-safe core dependencies, optional test/full extras, and a compatibility setup shim |
| P0 | Tag releases created GitHub notes but no distributable package, checksums, test evidence, or provenance | Release workflow now gates on tests/coverage, builds sdist/wheel, runs Twine validation, emits SHA-256 checksums, uploads evidence, and attests artifacts |
| P1 | Docker publication targeted a different Docker Hub namespace (`trojan3877`) | Tag workflow now publishes API/dashboard images to this repository owner’s GitHub Container Registry namespace |
| P1 | Deployment examples used mutable `latest` images and a mismatched registry | Helm and raw Kubernetes defaults now use the versioned GHCR API image; manual deployment requires an explicit image tag |
| P1 | Container bases did not match the package’s stated Python support | Core API and dashboard Dockerfiles now use Python 3.11 |
| P2 | Dependency review was not a CI gate | CI and release workflows now run `pip-audit` against the CI dependency set |
| P2 | README did not provide a package/release/evidence contract | Replaced with installation, scope, release artifact, checksum, registry, reproducibility, and limitation documentation |

## Open release blockers for production or consequential use

| Priority | Unresolved risk | Why it blocks production/consequential use |
|---|---|---|
| P0 | No vehicle integration, hazard analysis, safety case, independent verification, or certification evidence | The repository cannot support vehicle-control or safety claims |
| P0 | The external geocoding adapter uses provider text matching rather than deterministic geometry | Network/provider behavior and response text cannot be a geofence safety boundary |
| P1 | Dependencies are compatibility-bounded but not hash-locked | A clean install can resolve different transitive packages over time; generate platform-specific lockfiles before a production release |
| P1 | Workflows use version tags for third-party GitHub Actions rather than immutable commit SHAs | Pin actions to reviewed SHAs and maintain an action-update process for a hardened supply chain |
| P1 | No measured vehicle/simulator end-to-end latency, GPS-noise error, fault-injection, recovery, privacy, or model-quality evidence | Do not infer timing, accuracy, availability, or safety properties from unit tests or microbenchmarks |
| P2 | The optional full/GPU stack is not exercised by the core release gate | Add separate matrix jobs with recorded CUDA/Torch compatibility and hardware provenance before supporting those paths |
| P2 | Container, Helm, and Terraform changes are not rendered/scanned in the release workflow | Add image scanning with fail thresholds, SBOM retention, `helm lint/template`, policy checks, and staged deployment verification |

## Release acceptance conditions

Before calling any future release more than a prototype, close the P0/P1 items above with committed evidence. At a minimum: hash-lock dependencies, pin actions, validate and scan containers, exercise Helm templates, keep test/coverage artifacts, attach benchmark provenance, and maintain explicit release rollback instructions.

Until then, labels, release notes, documentation, and deployments must retain the prototype/simulation-only safety boundary.
